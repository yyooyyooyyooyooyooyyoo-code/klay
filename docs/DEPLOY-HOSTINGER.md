# Deploying to Hostinger (production)

Production is **https://klayconsultants.com** (no `www`) on Hostinger Business Web Hosting (LiteSpeed web
server). The site is fully static: `npm run build` writes every page as HTML into `dist/`, and the
**contents** of `dist/` are uploaded into `public_html`. No Node.js, PHP or database runs in production.

Netlify is only a preview/showcase. Every Netlify response carries `X-Robots-Tag: noindex, nofollow`
(set in `netlify.toml`), so it never competes with the real site in search. Never point the domain at Netlify.

## What the build produces for Hostinger

`npm run build` (via `scripts/seo.cjs` and `scripts/prerender.mjs`) adds these files to `dist/`:

| File | Purpose |
| --- | --- |
| `.htaccess` | `DirectoryIndex index.html`; one 301 from `http://` and `www.` to `https://klayconsultants.com`; `/index.html` and `/<path>/index.html` 301 to the folder URL; every redirect from `_redirects` (old article URLs, `/blog-img/*.png`, `/contact`, `/business-setup`); old WordPress `/category/`, `/tag/`, `/author/`, `/feed/` (and `/<anything>/feed/`), `/page/N/` URLs to `/blog/`; old WordPress sitemaps (`sitemap_index.xml`, `post-sitemap.xml`, `wp-sitemap*.xml` ...) to `/sitemap.xml`; `410 Gone` for `wp-admin`, `wp-login.php`, `xmlrpc.php` and any `.php`; `ErrorDocument 404 /404.html`; security headers; Cache-Control for HTML, sitemaps, `robots.txt`, `llms.txt` and favicons; compression; blocks hidden files except `.well-known`. |
| `assets/.htaccess`, `images/.htaccess`, `videos/.htaccess` (and `fonts/.htaccess` if that folder exists) | Cache-Control for each folder: `assets/` 1 year immutable (hashed names), the others 30 days. |
| `404.html` | The not-found page (noindex). |
| `sitemap.xml` + `sitemap-*.xml`, `robots.txt`, `llms.txt` | Crawl files, regenerated on every build. |
| `_redirects` | Netlify format; not used by Hostinger (the `.htaccess` blocks it). Harmless to upload. |

All `.htaccess` files are generated; never edit them on the server. Change the source data instead (see
the README "Redirects" section) and rebuild. `npm run build` fails if `dist/.htaccess` is missing a
redirect from `_redirects`, or if one of its rules would catch a real page or file.

## 1. Back up the current site (before touching anything)

1. hPanel > **Websites** > klayconsultants.com > **Files** > **Backups**: generate a new backup, then
   download both the **files** backup and the **database** backup (the WordPress database).
2. hPanel > **File Manager** > `public_html`: also download these individually, they are small and easy
   to lose track of:
   - `.htaccess` (the old WordPress file; it may contain custom rules). Enable **Show hidden files** in
     File Manager settings to see it.
   - `llms.txt` (generated by the old SEO plugin).
   - `wp-config.php` (database credentials, needed for a rollback).
3. **While WordPress is still running**, export the redirects it keeps in its database (they are not in
   `.htaccess` and are lost silently when WordPress goes): Rank Math > **Redirections** > **Export**, or
   Tools > **Redirection** > **Import/Export** (Redirection plugin), or Yoast SEO Premium > **Redirects**.
   Also export the plugin's **404 log** if it has one (old URLs that visitors and crawlers still request).
4. Keep the downloads somewhere safe until the new site has run without problems for a few weeks.

Open the old `.htaccess` and look for anything that is not WordPress or LiteSpeed Cache boilerplate
(for example custom redirects or IP blocks). Do the same with the exported plugin redirects and the 404
log. Anything still needed must be added to the project's redirect data (`BLOG_REDIRECTS` in
`src/content/blog/posts.ts` or `scripts/legacy-image-redirects.json`) or, for non-redirect rules, to
`buildHtaccess()` in `scripts/seo.cjs`, then rebuilt.

Old media URLs (`/wp-content/uploads/...`, found in Google Images results, backlinks and PDFs) have no
redirects in the project. Step 3 below therefore keeps `public_html/wp-content/uploads/` in place: it is
static files only, and the new `.htaccess` answers any `.php` request with `410 Gone`, so nothing in it can
run. Alternatively, export the media list and add 301s to `scripts/legacy-image-redirects.json` (to
`/images/blog/*.webp`) for the images that have traffic or backlinks, then move `uploads/` out as well.

## 2. Build locally

```bash
npm ci
npm run build
```

The build must end with `SEO validation passed ...`. Then zip the **contents** of `dist/` (not the
`dist` folder itself), including the hidden `.htaccess` files:

```bash
cd dist && zip -r ../klay-dist.zip . && cd ..
```

On Windows without `zip`, use PowerShell (`Compress-Archive` includes hidden files):

```powershell
Compress-Archive -Path dist\* -DestinationPath klay-dist.zip -Force
```

Check that `.htaccess` is at the top level of the zip (not inside a `dist/` folder).

## 3. Clear WordPress out of public_html

1. If the **LiteSpeed Cache** WordPress plugin is active, purge its cache first (WordPress admin >
   LiteSpeed Cache > Toolbox > Purge All) or, if WordPress is already gone, hPanel > **Advanced** >
   **Cache Manager** > purge all. The plugin itself becomes irrelevant once WordPress is removed.
2. In File Manager, create a folder **outside** `public_html` (for example `~/wordpress-old/`) and
   **move** into it everything in `public_html` that belongs to WordPress: `wp-admin/`, `wp-includes/`,
   all `wp-*.php` files, `index.php`, `xmlrpc.php`, `license.txt`, `readme.html`, `.htaccess`, `llms.txt`,
   and any other leftovers. From `wp-content/`, move everything **except** `wp-content/uploads/`
   (plugins, themes, cache, `index.php` ...), so old media URLs keep working (see step 1). Copy
   `wp-content/uploads/` into `~/wordpress-old/` as well, so the backup is complete. Then delete any
   `.htaccess` and `.php` files left inside `public_html/wp-content/` (a `.htaccess` there would override the
   root rules, including the `.php` 410).
3. **Keep** `public_html/.well-known/` if it exists (SSL validation and other verification files).
4. `public_html` should now be empty apart from `.well-known/` and `wp-content/uploads/`.

Moving (instead of deleting) makes a rollback a two-minute job. Delete `~/wordpress-old/` only after the
new site has been stable for a few weeks.

## 4. Upload the new site

1. File Manager > `public_html` > **Upload** `klay-dist.zip`.
2. Right-click the zip > **Extract** into `public_html` (the current folder, not a subfolder).
3. Delete `klay-dist.zip` from `public_html`.
4. With hidden files shown, confirm `public_html/.htaccess`, `public_html/index.html`, `public_html/404.html`,
   `public_html/assets/.htaccess` and `public_html/images/.htaccess` exist.

For later updates: build, zip, upload and extract again, overwriting existing files. Hashed files in
`assets/` from older builds can be removed occasionally (delete `public_html/assets/` before extracting).

## 5. SSL

hPanel > **Security** > **SSL**: the certificate for `klayconsultants.com` and `www.klayconsultants.com`
must be **Active**. If not, install the free certificate and wait until it shows Active. Do not enable
hPanel's "Force HTTPS" toggle in addition: the `.htaccess` already redirects http and www to
`https://klayconsultants.com` in a single 301 (two layers of redirects can create a redirect chain).

If the Hostinger CDN is enabled, purge its cache after every upload (hPanel > **Performance** > **CDN**).

## 6. Check the live site

In a private browser window:

- https://klayconsultants.com/ loads; http://klayconsultants.com/, http://www.klayconsultants.com/ and
  https://www.klayconsultants.com/ each end there after **one** redirect.
- A blog article, for example https://klayconsultants.com/blog/ then any article from the list.
- An old WordPress article URL under `/blog/`, for example
  https://klayconsultants.com/blog/tourist-bank-accounts-in-the-uae redirects (301) to
  https://klayconsultants.com/tourist-bank-accounts-in-the-uae/.
- An old image URL, for example
  https://klayconsultants.com/blog-img/UAE%20Golden%20Visa%20Guide%202026.png redirects to
  `/images/blog/uae-golden-visa-guide-2026.webp`.
- https://klayconsultants.com/category/blog/ and https://klayconsultants.com/feed/ redirect to `/blog/`.
- https://klayconsultants.com/does-not-exist/ shows the "Page not found" page with status 404.
- https://klayconsultants.com/wp-login.php returns 410; https://klayconsultants.com/.htaccess returns 403.

Headers, from any terminal (Git Bash on Windows):

```bash
curl -sI http://www.klayconsultants.com/about/ | grep -iE '^(HTTP|location)'
# HTTP/1.1 301 ... Location: https://klayconsultants.com/about/

curl -sI https://klayconsultants.com/ | grep -iE '^(HTTP|strict-transport|x-content-type|x-frame|referrer-policy|permissions-policy|cache-control|x-robots-tag|content-encoding)'
# 200; the five security headers; Cache-Control: public, max-age=0, must-revalidate; NO x-robots-tag

curl -sI -H 'Accept-Encoding: br, gzip' https://klayconsultants.com/ | grep -i content-encoding
curl -sI https://klayconsultants.com/sitemap.xml | grep -i cache-control      # max-age=3600
curl -sI https://klayconsultants.com/blog/tourist-bank-accounts-in-the-uae | grep -iE '^(HTTP|location)'
curl -sI https://klayconsultants.com/does-not-exist/ | head -1                  # 404
```

To check any `assets/` file's Cache-Control (`max-age=31536000, immutable`), copy a `/assets/...js` URL
from the page source and run `curl -sI` on it.

If the security or Cache-Control headers are missing, the server is ignoring `.htaccess` header rules:
contact Hostinger support and ask for `mod_headers`/`.htaccess` `Header` support (redirects keep working).

## 7. Google Search Console

1. Property for `https://klayconsultants.com` (a Domain property also covers `www` and `http`).
2. **Sitemaps**: submit `https://klayconsultants.com/sitemap.xml` (the index lists the page, service,
   blog and image sitemaps). Remove any old WordPress sitemap entries (`sitemap_index.xml`, `wp-sitemap.xml`
   and the like) that are listed there.
3. **URL Inspection**: inspect and "Request indexing" for the home page, `/services/`, `/blog/` and two
   or three articles. Also inspect one old redirected URL to confirm Google sees the 301.
4. Over the following weeks, watch **Pages** (indexing) and **Crawl stats** for 404s; add a redirect for
   any old URL that still gets traffic and rebuild.

## Rollback

1. In `public_html`, move the new site's files out (or delete them), keeping `.well-known/`.
2. Move everything from `~/wordpress-old/` back into `public_html`, including the old `.htaccess`.
3. If the database was changed or removed in the meantime, restore it from the hPanel backup
   (**Files** > **Backups** > database restore) or import the downloaded SQL file in phpMyAdmin.
4. Purge the LiteSpeed cache (hPanel > **Advanced** > **Cache Manager**) and the CDN cache if enabled.
5. Resubmit the WordPress sitemap in Search Console if it was removed.

## Other hosts

- **Netlify** (preview only): `netlify.toml` builds with `npm run build` and publishes `dist/`; redirects
  come from `dist/_redirects`; every response is `noindex, nofollow`.
- **Node** (`npm start`, `server.js`): serves `dist/`, applies `_redirects`, sends the same security and
  cache headers. Behind a TLS-terminating proxy, set `CANONICAL_HOST=klayconsultants.com` to redirect
  other host names and plain http to `https://klayconsultants.com` (the proxy must send `X-Forwarded-Proto`).
